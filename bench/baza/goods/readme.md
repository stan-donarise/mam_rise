# $rise_bench_baza_goods

## Шарды: 64 или 256 записей в одной Area

Дополнительные схемы `storage=shard64` и `storage=shard256` сохраняют поля
нескольких последовательных записей в общей Area. Число областей записей —
`ceil(N / размер шарда)`. В каждом шарде у записи свой Head и отдельные CRDT-поля;
значения не объединяются в JSON-атом. Список ссылок остаётся в корневом Land.
Color и Status индексируются так же, как в варианте Area на запись:
каждый индекс в отдельной Area, bucket — CRDT-список ссылок.

Шард выбирается по `floor(порядковый номер записи / размер шарда)`.
Последние записи находятся рядом, поэтому первый экран обычно читает один
шард, а на границе — два. Поиск по названию по-прежнему не индексирован:
первый запрос после F5 дочитывает оставшиеся шарды. Это блочное размещение,
не hash-распределение и не фиксированные 64/256 корзин.

```powershell
node rise/bench/baza/goods/playwright/goods-reload.js --matrix --shards-only --all-schemas --isolate-reload-tests
node rise/bench/baza/goods/playwright/goods-reload.js --matrix --shards-only --all-schemas --sizes=500 --boundary-check --isolate-reload-tests
```

Основная матрица — 500/1000/2000/4000/8000, четыре сочетания размера шарда и
состава. Проверяется число реально созданных областей, сохранение в IndexedDB,
три F5 без скролла и без предварительной загрузки всех шардов, поиск,
пересечения фильтров, редактирование, добавление и перестроение индексов.
Отдельный граничный прогон добавляет записи до 513: новая Area должна
появиться при записи 512; после F5 проверяются запись и членство в индексах.

Подготовка пустого профиля отделена от создания записей. Перед созданием
набора завершается `auth.current().pass()` — это штатная инициализация автора,
без подстановки ключей. Исследовательские прогоны с зависшим `land_grab`
до первой записи не характеризуют стоимость создания шардов. Адаптация
порядка инициализации выполнена только в нашем модуле; библиотеки не менялись.

## Матрица пользовательских операций с лимитом двух минут

```powershell
node rise/bench/baza/goods/playwright/goods-reload.js --matrix --all-schemas --isolate-reload-tests
```

Двадцать изолированных наборов: 500/1000/2000/4000/8000 записей × один Land/отдельные Area
× сокращённый/расширенный состав. «4 свойства» — Id, Title, Color, Status.
«10 свойств» — Id, Title, Checked, Uri, Color, Status, Quantity, Supply, Description, Tags;
Tags содержит пять ссылок на теги. Существующие расширенные наборы сохранены;
сокращённые используют отдельные ключи, без каталога тегов и лишних атомов.
для Area также сохраняются индексы Color и Status.

Измеряются создание до первого заполненного экрана, подтверждение сохранения
в IndexedDB, три F5 до первого экрана, холодные фильтры Color и Status,
пересечение фильтров (в том числе пустое), холодный и повторный поиск,
поиск без совпадений и его очистка, добавление, изменение статуса,
перестроение индексов Area и сброс выбранного набора.
После F5 прокрутки и предварительного чтения всех сущностей нет.

У каждой операции внешний Node-таймер на 120 секунд, независимо от блокировки
главного потока страницы. При превышении браузер закрывается и начинается
следующий набор. Зависимые операции незавершённого набора не измеряются:
нельзя выдавать F5 неполных данных за F5 запрошенного количества записей.
Результаты сохраняются после каждого шага в `artifacts/reports/matrix.json`.
Весь прогон использует один снимок `web.js`; до создания проверяются выбранный
состав, его привязка к таблице и подписи переключателя, исключая старую сборку.

Для создания и действий используется время от запуска пользовательского
действия до подтверждённого состояния и двух animation frame. Поиск также
сохраняет более точный замер от input-события, F5 — от начала навигации.
Время создания объектов после подготовки Land сохраняется отдельно.
F5 повторяется трижды, перед независимыми холодными Color/Status/поиском;
сравниваются первый экран, количество DOM-строк, прочитанные Land и long tasks.
Встроенные unit-тесты завершаются перед созданием, чтобы не конкурировать с ним.
Каждый набор использует новый browser context; база пользователя не меняется.

Для повторов без служебных unit-тестов во время F5 добавьте
`--isolate-reload-tests`. Первый запуск по-прежнему дожидается прохождения
unit-тестов; последующие F5 загружают только приложение. Это исключает гонку
миграций тестовой `$mol_db_test`: быстрая перезагрузка может прервать очистку
после открытия версии 3, а следующий тест пытается открыть версию 2.
Giper Baza использует другую базу `$giper_baza_mine` с версией 3.
Исходники библиотек не изменялись.

Открыть: http://localhost:9080/rise/bench/baza/goods/-/test.html

1. В левой панели «Настройки» выбрать «Один Land на все записи» или «Своя Area на каждую запись» и размер «1000», «3000» или «10000», затем нажать «Создать записи».
2. Таблица появится автоматически; прокрутить список.

Последняя созданная запись показывается сверху, включая результаты поиска.
«Добавить запись» добавляет одну запись в выбранный набор (или создаёт пустой набор
и первую запись), «Сбросить» сбрасывает только выбранный набор, поиск и фильтры.
Другие комбинации схемы/размера не затрагиваются. Reset отсоединяет локальную
ссылку на набор: физическая очистка CRDT-хранилища не выполняется.

Переключатель связан с URL-параметром `storage` и сохраняет выбранный
режим после F5. У режимов отдельные локальные наборы данных;
переключение не мигрирует и не пересоздаёт существующие записи.
Размер сохраняется в URL-параметре `count`; шесть комбинаций схемы
и размера имеют отдельные наборы. Существующие данные на 1000 записей
сохранены под прежними ключами. На время создания переключатели блокируются.

Приложение использует `$mol_book2`: настройки слева, таблица справа.
У настроек есть русские подписи; подписи таблицы оставлены как в исходном демо.
Под действиями расположены поиск и селекты
цвета и статуса; «All colors» и «All statuses» отключают соответствующий фильтр.
Подписи и значения этих фильтров оставлены на английском, как в таблице.
Фильтры и поиск объединяются через «И» и реагируют на изменение полей записи.

В настройках доступен поиск по названию: без учёта регистра, все слова
запроса должны встречаться в названии. Совпадения подсвечивает штатный
`$mol_dimmer`. Escape или крестик очищает поиск. Без запроса сохраняется
ленивое чтение только видимых записей; поиск по всему набору читает
Title каждой записи, без отдельного индекса.

Ссылки названий сохраняют привязку `uri` исходного компонента:
они ведут на товар, а не на текущую страницу, и не подсвечиваются как текущие.

Набор названий воспроизводим: десять брендов, десять моделей и десять
видов товаров, например `Aurora Wireless Keyboard 00004`.
Новые данные сохраняются под отдельным ключом `dataset_names2`:
для обновлённого набора нужно нажать «Создать записи» в каждом режиме.
Старые синтетические наборы не удалены и не перезаписаны.

Таблица открыта сразу, в том числе после F5. Информационной строки
со счётчиком и кнопок показа/скрытия нет. Кнопка создания остаётся.
Приведённые ниже старые замеры скрытого списка — история эксперимента,
а актуальный reload-сценарий измеряет F5 до заполненного окна таблицы.

Используется `$mol_list_demo_table`: те же checkbox, ссылка, select цвета,
switch статуса, number и date. ID, Checked, Title, Uri, Color, Status,
Quantity и Supply хранятся отдельными CRDT-полями сущности. Все 1000
сущностей и список ссылок по умолчанию находятся в одной land, без шардов и индексов.
Данные синтетические и воспроизводимые. Генерация названий не случайная.

Строка собрана на `$mol_view`. По запросу пользователя возвращены отступы,
промежутки между колонками и выравнивание по верхнему краю, как в исходном демо.
Описание и теги идут отдельной строкой ниже основных колонок.
Минимальная CSS-высота 96px согласована с оценкой списка в исходном демо:
без этого прыжок вниз мог оставлять последнюю строку за виртуальным окном.
Дата в интерфейсе показана как `дд.мм.гггг`, формат хранения не изменён.

Это локальный бенчмарк: master-соединения выключены только в этом модуле.

Новые записи дополнительно содержат `Description` (отдельный текстовый атом)
и `Tags` (CRDT-список пяти разных ссылок). В каждом наборе создаются 20 общих
сущностей тегов с `Title`, в основной Land набора; ссылки на них переиспользуются
между товарами. В режиме Area поля товара, включая список ссылок, находятся
в Area товара. Описание и имена тегов отображаются ниже основных колонок.
Старые наборы читаются без этих полей и не изменяются при рендере: для полного
обновлённого набора нажмите «Сбросить», затем «Создать записи».
Старые замеры ниже относятся к восьми полям, без описания и тегов.
При записи ссылки в другую Area создаётся отдельный экземпляр `Link`:
в `giper/baza/link/link.ts` метод `toBin()` кеширует относительные байты
в `_bin` без учёта смены базового Land. Переиспользование экземпляра,
декодированного в каталоге, иначе меняет цель ссылки при записи в Area.
Адаптация находится только в этом приложении; Giper не изменён.

## Индексы Color и Status

Только в режиме Area набор хранит атомы-ссылки `Color_index` и `Status_index`.
Каждый ссылается на собственную индексную Area (отдельный Land с теми же правами).
Внутри находятся `Ready` и CRDT-списки ссылок `bucket:red`, `bucket:green`,
`bucket:blue` или `bucket:minor`, `bucket:major`, `bucket:critical`.
Основной Land не содержит эти списки. В режиме одного Land индексы не создаются.

Новый набор строит индексы перед публикацией ссылки на набор. Добавление одной
записи дополняет готовые индексы, не перечитывая все Area. Изменения через
редакторы Color/Status обновляют членство в корзинах. При фильтрации пересекаются
индексные ссылки с основным списком; поля найденных записей нужны только для
видимых строк. Поиск по названию не индексирован и читает названия кандидатов.

Для старого набора нажмите «Перестроить индексы»: это явный полный проход.
Если ссылки на индекс нет или `Ready` не установлен, фильтр использует полный
проход вместо потенциально неполного индекса. Перестроение также очищает
устаревшие корзины и не создаёт дубликаты членства.

Это локальный бенчмарк, не транзакционная система: обновления нескольких Land
не атомарны. `Ready=false` сохраняется на время записи; незавершённый индекс
можно перестроить. Прямые изменения атомов в обход редакторов приложения и
параллельная работа разных клиентов требуют дополнительного протокола
согласования; этот вариант не обещает их автоматическое восстановление.
Проверки сетевой доставки сюда не входят.
Реактивный корень `yard().sync()` удерживается содержимым приложения.
Существующие данные после перезагрузки читаются из сохранённой ссылки;
приложение не создаёт новые записи в рендере и не запускает создание повторно.

и uncaught browser errors, помимо данных, долговечности и прокрутки.

### Создание, открытие и поиск — текущий сценарий

```powershell
node rise/bench/baza/goods/playwright/goods-reload.js --timing-only
node rise/bench/baza/goods/playwright/goods-reload.js --area --timing-only
node rise/bench/baza/goods/playwright/goods-reload.js --3000 --timing-only
node rise/bench/baza/goods/playwright/goods-reload.js --area --3000 --timing-only
```

Каждая команда создаёт изолированный локальный набор. Создание измеряется
один раз: отдельно заполнение объектов после подготовки root land и
время от клика до заполненного первого окна. Сохранение в IndexedDB
подтверждается до перезагрузки, но не включено во время создания.

Затем выполняются три F5, каждый из которых сбрасывает JS-кеши, сохраняя
IndexedDB. Измеряется время от начала навигации до готового окна из 11
строк (включая запуск приложения и отрисовку, не только распаковку CRDT),
long tasks и реально прочитанные области.

После каждого F5 выполняется первый поиск `Aurora Keyboard` (10/30
совпадений), затем прогретый `Keyboard` (100/300 совпадений). Время поиска
считается от браузерного input-события до отображения результатов и двух
animation frame, включая чтение недостающих сущностей и подсветку.
Это не отдельный микробенчмарк сравнения строк. Поиск сканирует все Title,
индекса нет. JSON с тремя отдельными замерами сохраняется в `reload.json`.

Флаг `--timing-only` исключает дополнительный CPU-профиль и полную
проверку всех полей из этого прогона; обычный сценарий их сохраняет.
Сборка приложения фиксируется на время прогона. Служебный audit и hot
reload исключены; `web.test.js` остаётся частью используемого `test.html`.
